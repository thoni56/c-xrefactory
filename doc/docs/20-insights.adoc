=== Yacc semantic data

As per usual a Yacc grammar requires each non-terminal to have a type.
Those types are named after which types of data they collect and
propagate.  The names always starts with `ast_` and then comes the
data type.  For example if some non-terminal needs to propagate a
Symbol and a Position that structure would be called
`ast_symbolParameterPair` ("Pair" being thrown in there for good
measure...).

Each of those structures also always carries a begin and end position
for that structure.  That means that any "ast" struct has three
fields, `begin`, `end` and the data.  The data are sometimes a struct,
like in this case, but can also be a single value, like an `int` or a
pointer to a `Symbol`.

[plantuml, ast, png]
....

class ast_symbolPositionPair {
Position begin
Position end
}

ast_symbolPositionPair *-- SymbolPositionPair : data

class SymbolPositionPair {
Symbol *symbol
Position position
}

....


=== Editor Buffer Lifecycle in the Server

Date: 2026-03-17

Editor buffers created by the server during parsing (e.g., entry refresh <<08-algorithms.adoc#entry-refresh-pass-3,Pass 3>> parsing sibling CUs, or refactoring loading files) have `preLoadedFromFile == NULL` — they were loaded from disk, not preloaded by the client. After each request, `closeAllEditorBuffersIfClosable()` in `editor.c` frees all buffers that are closeable: `textLoaded && markers == NULL && preLoadedFromFile == NULL && !modified`.

This means **server-created editor buffers do not linger between requests**. On the next request, files are reloaded from disk with fresh content. This is important because:

* A user may edit and save a file between operations without triggering any c-xref action. The server must see the new disk content, not a stale buffer.
* After a refactoring modifies editor buffers, markers are freed by the refactoring cleanup (e.g., `freeEditorMarkerListAndMarkers` at the end of `renameAtPoint`), making the buffers closeable.
* `parseToCreateReferences` prefers an existing editor buffer over disk — so if a stale buffer lingered, it would parse old content even when the disk file had changed.

Client-preloaded buffers (`preLoadedFromFile != NULL`) are NOT freed — they represent the editor's view of the file and survive until the client sends updated content or (eventually) a close notification.

**Implication for `didClose`**: A `didClose` protocol message (analogous to LSP `textDocument/didClose`) is not urgently needed for correctness — the existing cleanup handles server-created buffers. It would primarily benefit client-preloaded buffers that the user has closed in the editor, allowing the server to fall back to disk content. This is an architectural nicety, not a bug fix.

=== The include edges are inputs, not knowledge

Date: 2026-11-04, WSL session `d25255b8`

A `TypeCppInclude` reference plays two roles.
It is knowledge, the position of an `#include` line, which browsing and Rename Module use.
It is also an edge in the include graph, from which freshness and the siblings are found.
`collectCUsIncluding()` walks them in the table, and `buildIncludeGraph()` copies them at the start of a request.

When a file changes, the two roles pull apart.
The knowledge should be removed (ADR-0035), but the edges are needed to find the goal.
Removing a CU's references would also remove its edges, so a request in a header would no longer find that CU.
That is why a changed CU still loses its references only when it is built (`remove-on-change`).

Make only asks the forward question: is this target out of date?
For that the edges from the previous build are enough, since a new edge only appears through a change in the target itself.
We also ask the reverse question, which CUs reach this file, because that is how the goal is found.
For that the previous build's edges are not enough.
A CU that starts including a header is not found from the header until it is parsed.

`tests/test_a_cu_that_starts_including_a_header_on_disk_is_among_its_includers` shows it (suspended).
`a.c` is rewritten on disk to include `h.h` and call `f`, and a push on `f` in `h.h` does not list that call.
The trace has `b.c` as the only sibling of `h.h`.
The scan ran on the first request only, when `a.c` had no include, and `a.c` was never parsed.
A held CU does not have the gap, since a held CU that is out of date is always built.

The idea is that a changed file gets its edges from its current content, by the lightweight scan.
So a change does two things: it removes the file's references, and it rescans the file's includes.
Both are facts about the file, so both belong on the remove line of the shape.
The removal then has to leave the edges alone, e.g. by giving them a reference type of their own that is never removed.
That keeps the table the only store.
And it is one more reason for the remove line to come before the goal.

Open questions:

* What the parse writes, the edge type or today's `TypeCppInclude`, and which writer wins (`include-edges`).
* The scan reads the disk, not held buffers. That should be fine, since a held CU that is out of date is built, and the parse writes its edges.
* The scan misses `<...>` includes, and takes includes that an `#ifdef` leaves out. An extra edge only costs a rebuild, but a missing one leaves a part missing without that being known.
* `collectInputs()` builds the graph before the removal pass, so either the rescan comes before it or the graph is built after the pass.
