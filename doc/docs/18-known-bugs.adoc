== Known Bugs

This chapter collects known bugs that are not yet fixed.
Each entry describes symptoms, analysis (when available), and suspected root cause.

=== GlobalUnused false positive for static functions in .y files

*Symptom:* `addRuleLocalVariable` (and likely other static functions in `yacc_parser.y`) is flagged as globally unused, despite being called in several yacc action blocks.

*Observed behaviour:*

- Positioning on a _usage_ in an action block and doing GotoDefinition correctly navigates to the definition in the `.y` file. Browsing from there shows all usages within the `.y` file.
- Positioning on the _definition_ and doing PUSH does _not_ find the usages in action blocks.

*Analysis:*

The symbol has two separate entries in the reference table for the same `.y` file:

1. One entry contains only the definition (line 1914, in the C code section after `%%`)
2. Another entry contains the declaration (line 52, in `%{ %}`) and all usages from action blocks (lines 279, 284, 306, 319)

GlobalUnused sees entry 1 (definition, no usages) and reports it as unused.

*Suspected root cause:*

The yacc parser creates a different scope or symbol context when parsing C code inside action blocks `{ ... }` vs. the top-level C sections (`%{ %}` and after `%%`). This causes the references to be stored under different keys in the reference table, splitting what should be a single symbol into two entries.

*Workaround:* None currently. The false positive can be ignored.



=== A refactoring can see a truncated reference set

*Symptom:* on a large project, a rename rewrites some occurrences and leaves the rest, with no warning. The definition is found correctly, so nothing looks wrong.

*Cause:* `collectCUsIncluding()` (`src/server.c`) stops collecting at `MAX_CUS_TO_REPARSE` (128) and stops widening the reverse-include frontier at `MAX_INCLUDE_WALK_FILES` (256). A refactoring push is in `needsReferenceDatabase` but not in `needsWholeProjectParsed`, so it takes whatever entry refresh has parsed. Past the cap that is a subset.

*Measured 2026-09-22* on `tests/test_ffmpeg`, one cold `-push` on `avcodec_open2` where it is declared in `avcodec.h`, which 713 `.c` files include:

[cols="1,1,1",options="header"]
|===
|  |caps 128 / 256 |caps 4096 / 8192

|references found |*13* |*25*
|wall clock |23.3 s |256 s
|peak RSS |28.5 MB |91.6 MB
|goto answer |`utils.c:542` |identical
|===

So a rename there rewrites 13 of 25 occurrences. Browsing survives a truncated set; rewriting does not.

*When it bites:* only when more than 128 CUs (transitively) include one header, so a project needs at least ~130 CUs. c-xrefactory itself cannot reach it — 79 CUs in `src`, worst header fan-in `log.h` at 39. systemd (642 CUs) and ffmpeg (2616) can.

*Why the caps exist:* removing the lexem-stream cache (ADR-0012) took a full ffmpeg parse from 1-2 minutes to 25, and the caps bound that.

*Direction:* put the refactoring pushes in `needsWholeProjectParsed` so they ask like search does — the parse-all there is uncapped and counts only never-parsed CUs, so a warm project is asked for little. Two things that needs: declining must *abort* the refactoring, where today `if (waitForUserConfirmation(msg)) { ...parse... }` has no else and simply proceeds; and `parseAllPromptFor()` ends in `default: assert(0)`, so each added operation needs its own prompt word. It applies to parameter manipulation as much as to rename.

*Workaround, if the caps stay:* re-issue the push. Pass 3 filters `fileNeedsParsing` before applying the cap, so each request parses 128 fresh CUs and they stay parsed — six rounds for `avcodec.h`. Next does not help: `OP_BROWSE_NEXT` is in none of the gates and walks the list copied at the push.

=== Header static: prototype and definition are two symbols

*Symptom:* For a `static` function declared and then defined in a header, renaming it
from a file that includes the header renames the definition and the calls but leaves the
prototype unchanged, so the code no longer compiles.

*Suspected root cause:* `setStaticFunctionLinkName` (`src/semact.c`) names a static after
the file it is in only for its definition. Other usages, like the prototype, are named
after the compilation unit being parsed, so the prototype becomes `main.c!helper` while
the definition is `helper.h!helper`.

*Test:* `test_static_declared_and_defined_in_header` (suspended; the note covers the
`exactPositionResolve` question to settle before fixing).

=== Push by name finds nothing on a cold start

*Symptom:* Pushing a symbol by name answers "No symbol found." unless some file
containing it has already been parsed.

*Suspected root cause:* Push by name is project-wide, but is not among the operations
that ask to parse all unparsed CUs first (see
<<08-algorithms.adoc#project-wide-operations,Project-wide Operations>>).

*Test:* `test_browsing_push_name_parses_whole_project` (suspended).

=== Token pasting that forms numbers

*Symptom:* Macros that paste numbers produce wrong symbols in the reference table.

*Analysis:* Three separate faults, each with its own suspended test. Fix them in this
order, because the other two tests assume the first is fixed:

. *Pasted numbers are recorded as symbols* (`1##0` gives the symbol `10`), because the
  result of pasting is always treated as an identifier. Test:
  `test_token_pasting_numbers`. Fixing it changes the passing
  `test_collate_const_suffix_pasting`, whose `expected` records `42UL` as a symbol.
. *Pasting with `.` drops the `.`* (`3##.##14` becomes `314`). Test:
  `test_token_pasting_float`.
. *`0x` in a macro body is not one token*: the lexer reads `0` and then `x`, which becomes
  the macro parameter, so `HEX(FF)` gives `0FF`. The fix is in the lexer's handling of
  preprocessing numbers and affects how every number is read. Test:
  `test_collate_hex_prefix_pasting`.

Whether numbers need the intermediate `a##b` entries that identifier pasting records is
left for the fix to decide.

=== A compilation unit deleted outside the editor is never let go

*Symptom:* Delete a `.c` file from the terminal while the server runs. Every project-wide
operation then asks "1 of 138 compilation units need reparsing", and answering yes gives
"Can't open file ... : No such file or directory". It asks again the next time. Seen
2026-09-23 on the WSL machine (session `a3efe465`), after deleting `src/xref_tests.c`.

*Suspected root cause:* Only entry refresh Pass 1 notices a deleted compilation unit, and
it looks only at files open in an editor buffer (`markFileAsDeleted` in `src/server.c`).
The parse-all check in `callServer` counts every compilation unit in the file table whose
`lastParsedMtime` is zero. For a missing file the reparse fails, and the mtime it then
records is zero again, so the file is counted on every request. Not verified with a test.

This is the deleted-file case of behind-the-back disk changes (see
<<10-roadmap.adoc#,Roadmap>>, Behind-the-back disk-change detection).

=== A stale snapshot keeps symbols the parser no longer makes global

*Symptom:* a fix that narrows a symbol's visibility has no effect in a running editor
session, and reparsing the whole project does not help. Seen 2026-09-24 on the Mac
(session `7c731c79`): after yacc semantic values stopped being globally visible, Unused
Symbols in Project still listed 378 `$N` entries, from a server that was running the
fixed binary. Its snapshot, `src/.c-xref/db`, had been written seventeen minutes before
the fix and held 306 `$`-named symbols.

*Root cause:* the snapshot has no visibility field. `CxFieldTag` (`src/cxfile.c`) carries
the symbol's type and storage but not its visibility, so
`scanFunction_SymbolNameForSnapshotLoad` stamps everything it loads `VisibilityGlobal`.
That is lossless only while the write side's filter holds — `skip VisibilityLocal` in
`writeReferencesFromMemoryIntoCxFile` — which is the invariant
<<06-principles.adoc#,Principles>> states. Whenever a symbol reaches the snapshot that
should not have, it comes back global for the life of the server, and reparsing cannot
repair it: `equalReferenceableItems` (`src/referenceableitemtable.c`) compares
visibility, so the freshly parsed local symbol is a *different* table entry from the
stale global one. The stale entry keeps its definition reference and goes on answering
every project-wide question.

The invariant is still not quite true. A snapshot written over `src/` on 2026-09-24 held
35 position-keyed (block-local) link names and 17 `$`-named ones, the latter semantic
values used in an action with no matching declared local — `addRuleLocalVariable`
(`src/yacc_parser.y`) never declares the typed-reference form `$<type>N` at all, so every
one of those resolves as an undeclared C identifier at file scope.

*Remedy:* remove the snapshot and restart the server. That is also the only way out of
the deleted-compilation-unit loop above, and it clears the shadow occurrences that
behind-the-back disk changes leave behind — common enough between the three that the
client should offer it as a menu entry rather than requiring an `rm` in a terminal.
