[[move-function-refactoring]]
=== Move Function Between Files

**Status**: Phase 1 complete (December 2024)

==== Use Case

Reorganize code by moving function definitions between source files while maintaining correctness. Essential for refactoring large codebases into better module structure.

**Example**: Extract a utility function from `main.c` to `utils.c`, automatically handling visibility changes and header declarations.

==== What Works Now

* Move a function from one source file to another
* Automatically removes possible `static` keyword (makes function externally accessible)
* Adds extern declaration to target file's header
* Adds an `#include` of the target's header to the source, unless it is already there
* Moves function decorations
* Works for both C and Yacc files

Comments are moved only if `c-xref-comments-moving-level` is set, and it is 0 by default.

==== Next steps

**Remove extern declaration**: Remove the moved functions extern declaration from the
  header file for the source, if the function was not static.

**Remove the forward declaration**: Remove a declaration of the moved function from the
  source file. A `static` one left behind breaks the build.

**Include management**: Add the `#include` directives the moved function needs to the target.

**Move Function to New Module**: Create the target `.c` and `.h`, with an include guard
  and the includes, and add the module to the build (and a mock for the unit tests).

**Move several functions at once**: Functions that move together, e.g. a function and its
  helpers, can stay `static`.

**Helper function detection**: Identify and optionally move static helper functions that
  the moved function depends on. Prevents broken builds.

**Smarter header placement**: Automatically find the right location in header files
  based on existing declarations and dependencies.

**Preview**: Show what will be changed before applying the refactoring.

**Show the target and the source afterwards**: Today the target is shown in both windows.

**Delete Function**: Remove a function definition and its declaration. Safety check warns
  if callers exist. Reuses the function boundary detection from Move Function and the
  unused detection logic to verify no references remain.

**Ask whether to move the comment**: The server supports `-commentmovinglevel=N` controlling
  how comments adjacent to a moved function are handled (none, single slashed/starred,
  all). The client sends `c-xref-comments-moving-level`, 0 by default, so no comment is
  moved. A y/n question when there is a comment should replace the customization.

[[make-static]]
=== Make Static

Make a function `static` if nothing outside its file refers to it, and remove its
declaration from the header. The check is unused detection, but only counting references
from other files.

A report of all such functions in the project would give the candidates. After a Move
Function the helpers that moved along are typical ones.

=== LSP Integration

**Status**: EXPERIMENTAL (January 2026)

==== Use Case

```plantuml
@startuml
Bob -> Alice : hello
@enduml
```

Language Server Protocol (LSP) integration enables `c-xrefactory` to work with modern editors and IDEs (VS Code, vim/neovim with LSP plugins, etc.) beyond Emacs. This opens c-xrefactory's refactoring and navigation capabilities to a much wider audience.

==== What Works

**Go to Definition** (`textDocument/definition`):

* Functions - Jump to function definition from any call site
* Global variables - Navigate to variable declarations
* Types - Find typedef and struct definitions

**File Parsing**:

* Files are parsed as they're opened in the editor
* Symbols become available for navigation immediately

==== Current Limitations

**Single-file scope**: Only symbols in the currently opened file are accessible. To navigate to a function in another file, you must first open that file.

**No local variables**: Go-to-definition doesn't work for local variables or function parameters. This works in Emacs mode but requires architectural changes for LSP.

**Missing LSP features**: Only `textDocument/definition` is implemented. Coming features:

* Find all references
* Hover information  
* Code completion
* Rename refactoring
* Organize imports

==== How to Use

See the README for LSP client configuration examples. Basic setup:

1. Build `c-xrefactory` with `make`
2. Configure your editor's LSP client to use `c-xref -lsp` as the server command
3. Open C or Yacc files
4. Use your editor's "go to definition" command

==== Related Work

* link:17-major-codebase-improvements.adoc[Chapter 17: Major Codebase Improvements] discusses the technical architecture
* Multi-file support requires include graph and on-demand parsing (foundational work described in Chapter 17)

==== Implementation Path

The LSP path reuses the native architecture rather than inventing its own — document
events are entry-refresh sync points (<<08-algorithms.adoc#,Algorithms>>). The steps:

1. *Use `referenceableItemTable`* (done) — the separate `referenceDatabase` was removed;
   `findDefinition()` queries the shared table, and `didOpen` calls
   `parseToCreateReferences()` to populate it.
2. *Project initialization on startup* — on `initialize` / first `didOpen`, run the native
   setup (`initializeProjectContext` → `loadFileNumbersFromStore` →
   `scanProjectForFilesAndIncludes`) for config, compiler include paths, the snapshot, and
   include structure. Care: reconcile the overlapping init with `initializeParsingSubsystem`.
3. *Reparse on document events* — `didOpen` / `didChange` reparse the file; `didSave`
   triggers <<08-algorithms.adoc#entry-refresh-pass-2,Pass 2>> (reverse-include reparse). Same `bringHeldFilesUpToDate` logic, but
   changes arrive in real time.
4. *Multi-file navigation* — with 1–3 the table holds references from all project files,
   so `definition` works across files with no new query mechanism; Pass 3 sibling parsing
   triggers lazily.

Exposing refactorings follows the three tiers in
<<10-roadmap.adoc#lsp-refactoring-reach,Roadmap: Reaching refactorings>>: standard requests
first, then code actions and `workspace/executeCommand` (stubs exist, with
`codeActionProvider` still disabled in `src/lsp_handler.c`), and custom methods only where
an operation needs interaction during the operation itself.

=== Rename function handles `expect`

Many unittest frameworks have a feature for isolating a unit, often referred to as
"mocks", in C the "unit" of mocking/stubbing/doubling is almost always a function. These
mocks need to understand how they should respond to a call. As they have no logic they
are "programmed" by expressing conditions and responses.

In particular, Cgreen, has an `expect()` which takes the function name as the first
parameter, and then constraints to apply and values to return. This is implemented using
CPP macros so the function name is just text, and cannot be detected using normal
C-parsing/analysis.

Renaming a function that appears in an `expect` will not rename that reference. This
will usually cause the unittest to fail, because there is no call to that, no longer
existin, function.

A handy extension of the "Rename Function" would be to find these using some special
magic and replace them too.

=== Migrate to project local config

Previously `c-xrefactory` promoted a user-central config file, `~/.c-xrefrc` which
contained the config for all projects by containing a section for each project. The "New
Project" wizard in the Emacs client created new sections in this file.

Since 1.9 the promoted model is a project local config file, a `.c-xrefrc` in the root
of the project tree. The main advantage is that it can be checked in to repo and it will
not contain absolute file paths.

The home config is no longer read, so a legacy project has to be migrated. It's fairly
easy to do by hand, but as a polishing touch, providing a client operation to do that
would be nice.

There is a natural trigger for this: a legacy user with only `~/.c-xrefrc` will get a
"No project found" prompt. Instead of only offering
"Create new project?", the client could check `~/.c-xrefrc` for a section matching the
current file, and if found, offer to migrate that section to a project-local `.c-xrefrc`.

=== Retry the request that created the project

**Status**: Planned

==== Background

When no `.c-xrefrc` covers the file, the server answers `PPC_NO_PROJECT` and the client asks "No project covers <file>, create new project?". Answering yes runs `c-xref-project-new`, which writes a `.c-xrefrc` in the project root, auto-detected from `.git`.

==== Problem

The operation that asked the question is then thrown away. `c-xref-server-dispatch-no-project` ends with `(error "Project created")` — flow control by error, as the comment there says — so the goto-definition or completion the user asked for never happens, and they have to repeat it.

It is a small annoyance today. It becomes the normal first contact with a new project once auto-discovery is the only way in, so it is worth fixing then.

==== Design

Keep the dialog and re-send the original request once the config is written, rather than unwinding. The request's dispatch data is still in hand at that point, so this should not need new plumbing — worth confirming before committing to it.

=== Diagnostics Buffer

**Status**: Partly done

==== Background

The server parses a compilation unit when a request needs it. An operation that is project-wide asks before parsing the rest, and entry refresh reparses what has changed before every operation. Parsing is therefore spread through a session instead of happening once. During this parsing, warnings and errors may occur (e.g., missing include files, syntax errors from missing `-D` defines). These are expected and harmless — `c-xrefactory` continues best-effort — but users benefit from seeing them to tune their `.c-xrefrc` (adding `-I` paths, `-D` defines, etc.).

==== What works now

What did not parse is collected in the buffer `*c-xref-diagnostics*`, with its position.
The buffer is in a mode derived from `compilation-mode`, so `RET` in it, and `M-g n` and `M-g p` from anywhere, go to the place.
The messages are grouped by the compilation unit whose parse found them, under a line `Analysing <file>`, as compile output is.
When a unit is parsed again its group is replaced and moved last, and a unit that parses clean has no group.
An answer that added messages ends with a notice, e.g. `2 new messages in *c-xref-diagnostics*, M-g n to visit`, with the user's own key for `next-error`.

The server sends these messages as `<log>` records, after an `<analysing>` record for the unit.
Every other message record is modal, or a line in the minibuffer, and `<error>` also abandons the operation.
A server's stdout and stderr cannot be used either, since they are the synchronisation stream, and the client stops with `SYNCHRO PROBLEM` on anything else there.

In the server, a message about the code goes through `parsingMessage()`, which gives the position of the lexem the parser got last.
The lexer and the preprocessor are ahead of the parser, so they use `parsingMessageAt()` with a position of their own, e.g. that of the `#include`.
They send nothing unless the server was started with `-errors`, which the client does, and nothing in the parses that only refresh other files.
So what is reported is what the request's own parse found.
A unit that is only reparsed to refresh it keeps its old group until it is parsed for a request again.
`warningMessage()` and `errorMessage()` stay for what an operation itself has to say, and those are modal.

==== What is left

* The user manual: the buffer, and `M-g n` and `M-g p`.
* The report below. The same missing header is reported by every unit that includes it, so a generated `config.h` included by two hundred files is two hundred messages and one fact.

==== What the report should contain

Distinct unresolved include names, each with a count of how many places wanted it.
The set of names is short even in a badly configured project.

Two triggers for the same report: after a whole-project parse, and on demand, which is how
a user asks whether the project is configured correctly.

==== Suggesting a fix

An include that is not found often has a file with that name somewhere in the project.
The report could then ask whether that is the one, and offer to add the `-I` for it to the
config, i.e. "`foo/bar.h` was not found, there is one under `lib/include/`. Add
`-Ilib/include`?".
After that the CUs that wanted it are out of date, since the config changed, and get
parsed again when needed.
More than one candidate is a menu, and none is just the report.

=== Unused Detection: Exclude Patterns

==== Background

The "Browse Global Unused" feature reports symbols that are defined but never used. In
practice, certain files produce noise that hides genuinely unused symbols:

* **Test files** (`*_tests.c`) — test functions are called dynamically by the test runner
  (e.g. Cgreen uses `dlsym`), so they appear unused to static analysis.
* **Yacc grammar files** — synthetic variables like `$`, `$1`, `$2` generated by the Yacc
  preprocessor show up as defined-but-unused.
* **`main`** — called by the runtime, so it is never used in the source.

The noise also goes the other way. A call from a unit test counts as a use, so a function
that only its tests call is not reported. When removing XrefMode, `xref()` was unused in
production but did not show up, because `xref_tests.c` still called it.

==== Proposed Behaviour

Support exclude patterns in the project configuration to suppress unused detection for
matching files:

[source]
----
[/path/to/project]
  /path/to/project
  -unused-exclude *_tests.c
  -unused-exclude *.y
----

Symbols defined in excluded files would be skipped during unused detection. Navigation
and refactoring would be unaffected — only the unused detection filter applies.

References from excluded files should probably not count as uses either. Then a function
called only from `*_tests.c` would be reported as unused in the production code.

==== Design

The exclude patterns would be stored as a `StringList` in `ProjectConfig` (or `options`)
and checked during the `mapAddGlobalUnusedSymbolsToHkSelection` iteration. The check
would match the filename of the definition reference against the exclude patterns using
the existing shell-glob matching logic.

=== Browsing includes

==== Background

The `#include` preprocessor statments are referenceable items just like typenames and
variables. That means it is logical to expect that placing the cursor on an `#include`
line and navigation would follow the same UX as for a variable: PUSH moves cursor to the
definition (in this case the file itself) and NEXT to the next "reference", which in
this case would be the next #include statement for that file.

This does not happen.

==== Design

This needs to be investigated and understood before an attempt to design a solution can be made.

=== Semantic Read-only Files (Include Path Ownership)

==== Background

Files discovered through `-I` include paths are currently treated the same as project-owned
files for navigation purposes. However, these files typically belong to external libraries
or shared code that the user should browse but not modify through refactoring operations.

For example, when a project uses `-I /shared/lib/include`, the user can navigate into
headers from that library. If a rename refactoring is performed on a symbol defined in the
project but also referenced in those external headers, the refactoring should not propagate
changes into the external files.

The legacy `c-xrefactory` treated all parsed files equally — there was no distinction
between "my code" and "code I depend on." This was acceptable when projects were
self-contained, but with the modern include-path-based project scope (see
link:06-principles.adoc[Principles, Project Scope]) the distinction matters.

==== Proposed Behaviour

Files discovered through `-I` paths (but not listed as source directories in the
configuration file) would be marked as **read-only for refactoring purposes**:

* **Navigation**: fully supported — PUSH, POP, search results all work as today
* **Refactoring propagation**: changes stop at the ownership boundary. A rename in
  project code does not modify files in `-I` directories. The user is informed that
  external references exist but were not updated.
* **Explicit override**: an advanced option could allow the user to opt in to
  cross-boundary refactoring for specific operations

==== Design

This requires a per-file or per-directory ownership flag in the file table, checked by
the refactoring engine before applying edits. The flag would be set during the lightweight
scan based on whether the file was discovered under a source directory (owned) or an
include path (read-only).

The exact mechanism and UX (warning, confirmation, or silent skip) need further design.

[[generic-selection]]
=== C11 `_Generic`

**Status**: Not implemented. Pinned by the suspended `test_parsing_generics`.

==== Use Case

`_Generic` selects an expression by the type of a controlling expression, most often to
pick one of several functions, as in `<tgmath.h>`:

[source,c]
----
#define cbrt(x) _Generic((x), float: cbrtf, long double: cbrtl, default: cbrt)(x)
----

Today `_Generic` is neither a keyword nor defined away, so it parses as an identifier and
every association is a syntax error. Error recovery keeps some references by chance but
loses others, such as the `default:` branch and a typedef used as an association type.

==== Design

Parse every association and record the references in all of them. Do *not* select the
branch the controlling expression's type would pick.

* Selecting needs the type of the controlling expression and C's type compatibility
  rules — compiler work that a cross-referencer does not otherwise need.
* Recording every branch is also what users want: renaming `cbrtf` must update the macro
  above even where every call site happens to use `double`.
* Defining `_Generic` away, the way `_Alignas` is in the fallback defines, would avoid
  the syntax errors cheaply but drop exactly the function references `_Generic` exists
  to choose between.

The grammar needs a `_Generic` keyword and a generic-selection rule with associations of
the form `type-name : assignment-expression` and `default : assignment-expression`.
Branch selection would only matter for navigation or completion on the type of the
result (`_Generic(...).field`), which is rare.

=== Inline Function and Inline Macro

**Status**: Not implemented.

==== Background

There is no way to inline a function or a macro. The case that asked for it was two
wrappers in `startup.c`, `saveMemoryCheckPoint()` and `restoreMemoryCheckPoint()`, that
only called `saveCheckpoint()` and `restoreCheckpoint()` with a fixed argument. Removing
them meant rewriting each call by hand, and deleting the declaration in `startup.h` and
the stub in `startup.mock`.

==== Proposed Behaviour

With the cursor on a function, or on a call to it, *Inline Function* replaces each call
with the body, the arguments substituted for the parameters, and removes the definition.
The declaration in a header and a stub in a `.mock` file go too. *Inline Macro* does the
same for a macro.

A body that is a single statement, or returns a single expression, is probably the case
to do first. Anything more needs more than text substitution. An argument with side
effects must not be evaluated twice, and a name in the body can collide with one at the
call site. Refusing with a reason is fine there.

==== First Slice

A body that is one statement, or `return expr;`, where no parameter is assigned or has
its address taken. Each argument replaces its parameter, in parentheses. The parameters'
references tell if they are assigned, so this needs no data flow analysis.
Both cases so far fit, the wrappers in `startup.c` and `displayingErrorMessages()`,
which only returns `options.errors`.

==== Bodies with More Statements

Extract Function copies the region verbatim and puts what is needed at the edges, e.g.
`int b = *_b;` first in the new function and `*_b = b;` last. Inline can do the same the
other way round. Each parameter becomes a local in a block, initialised with its
argument, and the body is copied verbatim:

[source,c]
----
x = f(a + 1, g());

/* becomes */
{
    int p = a + 1;
    char *q = g();
    /* the body of f() */
}
----

Each argument is then evaluated once, and a body that assigns to a parameter, or takes
its address, still works. Extract already makes such declarations from a local's link
name (`getLocalVariableDeclarationFromLinkName()`), and a parameter is a local.
A parameter that is never assigned, with an argument that is a name or a constant, can
still be replaced directly instead.

What is left is the `return`. A `return e;` last in the body becomes `x = e;`, or `e;`
if the value is not used. A call inside an expression has no room for a block, so there
only a body that is `return expr;` can be inlined. More than one `return` is refused.

Names can collide both ways. An argument can use a name that an earlier parameter's local
hides (`int p = p + 1;`). The body can use a global that a local at the call site
hides. Both show in the references, which say what each name resolves to.
A body with a `static` local, a recursive or variadic function, and a `goto` into the
body are refused.

The parts that exist are finding every call (as for Rename), the extent of a function
definition (Move Function) and the position of an argument at a call (the parameter
refactorings).

*Inline Macro* is closer, because a macro means its text. The arguments replace the
parameters verbatim, and only `#` and `##` need care.

=== Extract an Expression as a Function

**Status**: Not implemented. Issue #28.

==== Background

Extract Function only works on statements.
Marking part of an expression, e.g. one operand of `||` in an `if` condition, gives a `void` function, which is not what you wanted.
The case that asked for it was `isPreloaded(buffer) || buffer->modified` in `closeEditorBuffersNoLongerHeld()`, which had to be extracted by hand.

==== Proposed Behaviour

When the marked text is an expression, extract a function that returns it, with the type of the expression, and replace the text with a call.

If finding the type of the marked text proves hard, an explicit *Extract Predicate* could be an alternative.
The user then says it is a condition, and the function is always a `bool` one.
That probably covers most of the cases that come up.

=== Modernize Function

**Status**: Not implemented.

==== Background

Old C code often has K&R function definitions, where the parameter types are declared between the parameter list and the body.
There is no way to turn such a definition into one with a prototype.

==== Proposed Behaviour

With the cursor on a K&R function definition, *Modernize Function* (or *Prototype Function*) moves the parameter declarations into the parameter list.
A declaration without parameters elsewhere, e.g. `int f();` in a header, gets the same parameter list.
An implicit `int`, for the return type or for a parameter that is not declared, should probably be made explicit at the same time.

A parameter declared `char`, `short` or `float` is a catch.
A caller without a prototype in scope passes it promoted, to `int` or `double`, so adding the prototype changes how it is called.
Refusing, or at least warning, is probably right there.

=== Unify Parameter Names

**Status**: Not implemented.

==== Background

A parameter's name is given again in every declaration of its function, i.e. in the header, in a forward declaration, in the definition and in a mock.
Each is a symbol of its own, so Rename changes one of them.
Giving a parameter the same new name everywhere means one Rename for each definition, real and mock, and editing the declarations by hand.

==== Proposed Behaviour

With the cursor on a parameter, *Unify Parameter Name* asks for a name and gives the parameter that name in every declaration and definition of the function.
In a definition that is a rename of the parameter, uses included.
In a declaration it is only the name in the parameter list.
A declaration that has no name for the parameter could get one, or be left as it is.

=== Introduce Parameter Object

**Status**: Not implemented.

==== Background

Extract Function gives one parameter for each local the region uses, and an in/out pointer for each one it changes.
When the region works on a group of locals that always go together, the parameter list gets long.
The case that asked for it was the loop in `parseUnparsedSiblingCUs()` (`server.c`) that collects the sibling CUs.
Extracting it gave seven parameters.
Four of them were the selection being built, i.e. the array of file numbers, its count and two counters for what was skipped.

==== Proposed Behaviour

With some locals marked, *Introduce Parameter Object* (or *Group Locals into Struct*) asks for a type name, declares a struct with those locals as fields, and replaces them with one local of that type.
Every use becomes a field access, e.g. `selection.count`.
An Extract Function after that passes one pointer instead of four.

The same for a group of parameters that always go together is Fowler's original.
With the cursor in a parameter list and some parameters marked, it asks for a type name, declares a struct with those parameters as fields, and replaces them with one parameter of that type.
In the function body every use becomes a field access.
The simplest thing at the call sites is to pack the arguments there, since they are probably separate variables on the outside, e.g. `collectCUsIncluding(fileNumber, (CUList){cuFileNumbers, cuCount}, maxCUs)`.
Turning the variables at a call site into one struct as well is then the locals variant above.

A second case was `cuFileNumbers` and `cuCount`, which go together through `collectOutOfDateHeldCUs()`, `stripChangedHeldHeaders()` and `collectCUsIncluding()` (`server.c`).
There the count also comes back as the return value, so packing a copy at the call site is not enough.
Passing a pointer to the packed struct, and reading the count back after the call, would work, but is not pretty.
How the UI marks the parameters, and what to do with such a count, is not decided.

=== Extract Function with Jumps out of the Region

**Status**: Not implemented.

==== Background

Extract Function refuses a region that a `return`, `break`, `continue` or `goto` leaves ("There are jumps in or out of region", `makeExtraction()` in `extract.c`).
Only Extract Macro lets them through, since a macro is text and the jump lands where it was.
The case was the loop in `__has_include(<...>)` (`yylex.c`), which ends with a `break` at the `>` and a `return 0` at the end of the line.

The program graph already has what it takes to find them.
A `return` is a reference to the internal label `-1`, `break` and `continue` to the label of the innermost loop, and `goto` to the user's label (`jump_statement` in `c_parser.y`).
Each such node knows its target, which side of the region both are on, and its own position.
What the graph does not have is the value of a `return`, since a constant is no reference, and where the statement ends.
Both can be read from the text, from the position to the `;`.

==== Proposed Behaviour

The new function returns how it ended, and the call site acts on it:

[source,c]
----
int exit = newFunction_(...);
if (exit == EXIT_BREAK)
    break;
else if (exit == EXIT_RETURN)
    return 0;
----

It has to be `if` and not `switch`, since a `break` in a `switch` leaves the `switch` and not the loop.

The first case to do is probably a region that is only left by `return <constant>;`, or `return;` in a `void` function, and has no result of its own.
The new function then returns a `bool`, and the call is `if (newFunction_(...)) return 0;`.
A `break` out of a loop around the region comes next.
A region that already returns a value, or a `return` of a local's value, needs an out parameter as well, and could be refused to start with.

=== Inline Output Parameter

**Status**: Not implemented.

==== Background

For each local the region changes, Extract Function copies it in from a pointer parameter at the start of the new function and back at the end, e.g. `int cuCount = *_cuCount;` and `*_cuCount = cuCount;`.
That is safe, but the copies are usually the first thing you want gone.

==== Proposed Behaviour

With the cursor on such a parameter, *Inline Output Parameter* replaces every read of the local with `*_cuCount`, every write with an assignment through the pointer, and removes both copies.
The parameter then takes the local's name, `cuCount`, which is free now.
A read that is an operand gets parentheses, so `count++` becomes `(*count)++` and not `*count++`.
If the local was declared together with others, e.g. `char *name, type;`, only its declarator goes.
It should refuse if the address of the local is taken, or if not every return writes it back.

The steps for one parameter have to be applied together.
Done one at a time, the local is set but never read in between, and `-Werror` stops the build.

Turning a single in/out parameter into the return value is the natural next step, and could be a refactoring of its own.

=== Finish Extract Variable

**Status**: Partially implemented.

==== Background

*Extract Variable* replaces the marked expression with a new variable and declares it, initialized to the expression.
The declaration is always `int`, since the type of the expression is not known (`generateNewVariableDeclaration()` in `extract.c`).
It also goes in at the wrong place.
The line it is given is `currentFile.lineNumber`, i.e. probably wherever parsing was, not the start of the statement that held the expression.

Even so it was an immense help when generalizing a function.
Extracting the varying parts of a function body as variables first, and then extracting the function, gives them as parameters.
The case was `handle_invalid_request()` and `handle_method_not_found()` in `lsp_handler.c`, which differed only in an error code and a message.

==== Proposed Behaviour

The declaration gets the type of the expression, and goes in before the statement that held it.
This is the same type that *Extract an Expression as a Function* needs, so the two probably share it.

=== Inline Variable

**Status**: Not implemented.

==== Background

The generalization above ended with inlining the extracted variables again at the first call site, by hand.

==== Proposed Behaviour

With the cursor on a local that is assigned once, *Inline Variable* replaces each use with its initializer and removes the declaration.
It should refuse if the variable is assigned again, or if its address is taken.
An initializer with side effects, or one that reads something changed between the declaration and a use, makes the result differ, and is probably reason to refuse too.

=== Name and Define Constant

**Status**: Not implemented.

==== Background

A literal that means something, e.g. an exit code the protocol prescribes, is better as a name.
Today that is a `#define`, or an enum member, written by hand and then a search for the other occurrences.

==== Proposed Behaviour

With the cursor on a literal, *Name and Define Constant* asks for a name, defines it, and replaces the literal with the name.
Other occurrences of the same literal could be offered, but only the user can tell which of them mean the same thing.
The type does not tell either, e.g. two functions that return `LexemCode` can both return 0 for different reasons.
Where the definition goes, i.e. in the file or in a header, and as a `#define` or an enum member, is not decided.

=== Background Work

**Status**: Possible. Waits for the sweep (ADR-0033, `sweep` in `doc/backlog.md`).

==== Background

The server only works when a request arrives, and then the user waits.
Out-of-date knowledge outside every request's goal is never brought up to date, and on a large project the first request carries the whole initialization.
With the sweep, bringing knowledge up to date a part at a time is safe, since each step removes only what is shown to be false.

==== Proposed Behaviour

When no request is waiting, the server does one unit of work, e.g. builds the knowledge of one out-of-date CU, and then checks for a request again.
Answers fill in while you work, and a cold start answers what it knows at once.
Other candidates are the sweep itself, saving the snapshot, and checking the change times of inputs.

==== Design

The server has no threads and blocks in `readOptionsFromPipe()` until the next request.
With all its global state, threads are not an option, so the work would be cooperative: wait for input with a timeout, and work when it expires.
A parse cannot be interrupted, so a request may wait for one CU to finish.
