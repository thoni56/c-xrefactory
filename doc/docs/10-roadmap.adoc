== Roadmap

This chapter records where `c-xrefactory` is going — the architectural direction and the
feature vision. The mechanisms behind the "done" items live in their home chapters
(<<06-principles.adoc#,Principles>>, <<08-algorithms.adoc#,Algorithms>>); implementation
detail is in <<17-major-codebase-improvements.adoc#,Major Codebase Improvements>>.

=== Guiding Principles

* **Incremental improvement**: Each step should provide immediate value while moving toward long-term goals
* **Test-driven modernization**: Maintain 85%+ test coverage to enable confident refactoring
* **Backward compatibility**: Preserve existing Emacs workflows while enabling modern IDE integration
* **Architectural simplification**: Replace artificial mode distinctions with unified, smart on-demand behavior
* **Legacy code respect**: Work with the existing 1990s codebase thoughtfully, not against it

=== Convergence: Memory as Truth

In-memory references are the single source of truth — every operation (navigation,
search, completion, refactoring, unused detection) reads the in-memory
`referenceableItemTable`, and the `.cx` files are a disposable startup snapshot. This
convergence is **complete**; the mechanism lives in <<06-principles.adoc#,Principles>>
(Memory As Truth, Continuously Fresh References) and <<08-algorithms.adoc#,Algorithms>>
(Entry Refresh, Lightweight Scanning). What follows is status and what remains.

==== Done

* *Separate sync from dispatch* — entry refresh reparses stale files before every
  operation (link:/workspace/1/decisions/C-xrefactory#20[ADR-0020]).
* *Lightweight file-structure scanning* — CU and include discovery without full parsing
  (link:/workspace/1/decisions/C-xrefactory#22[ADR-0022]).
* *Refactoring as a server operation* — all refactorings run via `OP_REFACTORY`;
  `RefactoryMode` and the `-refactory` process removed.
* *Search from the in-memory table* — `searchInMemoryTable()` replaced the disk scan;
  the last disk-as-truth read is gone.
* *Disk snapshot* — `.cx` loaded and mtime-validated at startup, saved on exit and
  periodically; no mandatory `-create`.

=== Convergence: The Setup Ladder

Memory as Truth settled what is authoritative. This convergence settles _when_ each
thing is bound. Setup to full operation is a ladder of three steps, and the rule is
**nothing before it's known**: a thing is bound at the step where it first becomes
known, and no step guesses at what a later one settles.

. *Process start* — parsing setup only. Command-line options are process-scoped, so they
  are read here. No project, no config, no project settings.
. *`-getproject`* — discovery, the config, include paths, compiler interrogation, the
  snapshot load. No parsing.
. *Every request after* — uniform. Entry refresh, then parse what the request needs.

The ladder is climbed out of order today. `mainTaskEntryInitialisations()`
(`startup.c:827`) discovers a project at process start, from `cwd` when the command line
names no file, and reads that project's options before any request has arrived — see
<<06-principles.adoc#,Principles>> (Initialization). The lifetime partition that fixes it
is in <<17-major-codebase-improvements.adoc#,Major Codebase Improvements>> (Replace
Global `options` with Typed Requests).

==== Done

* *Single project per server* — the client restarts the server on a project switch, so
  the project tier can freeze once it is bound
  (link:/workspace/1/decisions/C-xrefactory#21[ADR-0021]).
* *Automatic config discovery* — `-getproject` finds the project from a file name, so
  naming a project on the command line is no longer how it is done
  (link:/workspace/1/decisions/C-xrefactory#5[ADR-0005]).
* *Uniform requests* — entry refresh reparses stale files before every operation, so
  step three needs no special cases
  (link:/workspace/1/decisions/C-xrefactory#20[ADR-0020]).
* *Structure without parsing* — the lightweight scan lets step two bind include
  structure without a parse (link:/workspace/1/decisions/C-xrefactory#22[ADR-0022]).
* *First fields off the blob* — `ProjectConfig.sourceDirs` is project-scoped state with
  an owner, and `ParsingConfig` is the same pattern one layer down.

=== Optimization

Once the core architectural path (lightweight scan, entry refresh, memory-as-truth) is functional, targeted optimizations can reduce cold-start latency and improve responsiveness on large projects.

==== Measured, 2026-09-23

Two different numbers, on the same tree — ffmpeg in `tests/test_ffmpeg`, 2615 compilation
units, 1.38M lines of `.c` and `.h`, on the maintainer's Mac:

* *Whole-tree parse* — 8m07s wall clock (user 7m47s), writing a 17.96MB snapshot. That is
  about 186ms per compilation unit, or ~2800 lines a second counting each CU's headers
  every time it sees them. The `test_ffmpeg` Makefile still says "~25 minutes" from an
  older measurement; the file count is unchanged and the snapshot is 3% *larger* than the
  13 August one, so the work is not smaller, it is faster.
* *Cold-start PUSH* — 42s for `AudioFIRContext` from `af_afir.c`: scan 2.7s, Pass 3 round
  one 19s, round two 19s (the second round from `<...>` includes the full parse
  discovers). This is the number the two rows below are about, and it has not been
  re-measured since.

The first is what a batch prime costs and what a progress estimate would divide; the
second is what a user waits for before anything appears.

[cols="1,3"]
|===
|Optimization |Description

|**Header-filtered sibling parsing**
|Entry refresh <<08-algorithms.adoc#entry-refresh-pass-3,Pass 3>> currently parses all CUs sharing _any_ header with the request file. On large projects this pulls in a large fraction of all CUs (e.g. on ffmpeg, navigating `AudioFIRContext` from `af_afir.c` triggers 2481 sibling CUs because of widely-shared utility headers). When the operation is navigation, only CUs sharing the header that _defines the navigated symbol_ are relevant. Filtering to that header reduces the scope dramatically: `AudioFIRContext` is defined in `af_afir.h`, which only 3 CUs include — so 2481 → 2 sibling CUs to parse. Challenge: Pass 3 runs during sync (before dispatch), but the symbol is only known during the operation. The solution must bridge this gap — e.g. by triggering targeted sibling parsing from the operation after the symbol's defining header is identified. Measured cold-start PUSH on ffmpeg `af_afir.c`: scan 2.7s, Pass 3 round 1 19s, Pass 3 round 2 19s (from `<...>` includes discovered by full parse), total 42s. Parsing dominates — the scan is not the bottleneck. Worst case: core API headers like `avcodec.h` (614 CUs) or `internal.h` (1171 CUs) — parallel parsing may be needed for these.

|**Extend scan to capture `<...>` includes**
|The lightweight scan currently only matches `#include "..."`. Projects like ffmpeg use angle-bracket includes for internal headers (with `-I` paths), so the scan misses roughly half the include structure. Extending to `<...>` requires header-filtered sibling parsing first — without that filter, ubiquitous system headers (`string.h`, `stdlib.h`) would cause Pass 3 to pull in nearly every CU in the project. Also needs care to avoid recursively scanning system headers outside the project tree.

|**Lexing cache re-introduction**
|The lexing cache (pre-tokenized file content) was present in the original codebase but lost during restructuring. Re-enabling it avoids repeated lexing of the same file across multiple parse passes.

|**Parallel parsing**
|Even with header-filtered sibling parsing, core API headers in large projects can fan out to hundreds of CUs (e.g. `avcodec.h` in ffmpeg is directly included by 614 CUs, `internal.h` by 1171). Parallel parsing of independent CUs could reduce wall-clock time roughly linearly with core count. The main challenges are: the global mutable state throughout the parser and symbol table (would require per-thread working sets with merge), CX memory allocation (currently a single arena), and the file table (shared, needs synchronization or partitioning). This is a significant engineering effort but may be the only way to achieve acceptable latency for navigation targets in widely-included headers.
|===

=== Feature Vision: LSP Support (explorative)

The last and least-defined direction: expose `c-xrefactory` through the Language Server
Protocol so VS Code, Neovim, and other LSP editors can use its navigation and — as far as
the protocol allows — its refactorings. How far that reaches is genuinely open. Basic
features (definition, references, completion) map cleanly, but `c-xrefactory`'s interactive
refactorings and symbol browsers have no natural LSP equivalent, so the Emacs client will
likely remain the gateway to its full refactoring power. Surfacing even some refactorings
in an LSP environment is the prize worth chasing; the reach is unknown until we get there.

See <<03-functional-overview.adoc#,Functional Overview>> for the current LSP state and
protocol limits, and <<11-planned-features.adoc#,Planned Features>> for the implementation
steps.

The one durable design point: *LSP document events are entry-refresh sync points.*
`didOpen` / `didChange` / `didSave` correspond exactly to the native path's preload and
un-preload staleness signals, and `definition` / `references` are operations over a table
those events have already made current. So the LSP path needs no architecture of its own —
it reuses entry refresh (<<08-algorithms.adoc#,Algorithms>>), triggered by different events.

[[lsp-refactoring-reach]]
==== Reaching refactorings: three tiers

The Emacs protocol is interactive and LSP is not, but most of that gap can be closed in
the server rather than in each editor. Every LSP editor gets what the server exposes
through standard requests. Anything beyond that needs client code, written once per
editor. So each operation should live in the lowest tier that can carry it:

1. *Standard requests.* Operations with a direct LSP counterpart: rename
   (`textDocument/rename`), references, definition, and unused symbols as diagnostics.
   These cost nothing per editor.
2. *Code actions and `workspace/executeCommand`.* The portable home for most
   refactorings: extract, move function, add, delete and reorder parameters. The server
   offers the actions that apply at the cursor or selection. Choosing one either carries
   a ready `WorkspaceEdit`, or runs a command where the server computes the edits and
   applies them with `workspace/applyEdit`. Editors show these in their refactoring
   menus with no client code.
3. *Custom methods plus editor extension code.* Only for real interactivity: asking for a
   name or parameter position, resolving ambiguities, the symbol browser, and yes/no
   questions during an operation. There are two shapes:
   the extension collects the answers up front and passes them as `executeCommand`
   arguments, or the server asks in the middle of an operation with a custom request
   (e.g. `cxref/askUser`) that the extension answers. The second is closest to the Emacs
   protocol, but every editor has to implement it. The standard
   `window/showMessageRequest` covers choices between buttons, not free text.

The aim is to keep tier 3 small. The more an operation's questions can be settled before
it starts, or turned into a choice between buttons, the more editors get it for free.

This also shapes how the server is packaged. The server itself is editor-neutral. Each
editor gets a thin extension that launches it and implements tier 3: a Node extension in
VS Code, a Lua plugin in Neovim, eglot or lsp-mode in Emacs, a Python plugin in Sublime,
a plugin (native LSP API or LSP4IJ) in JetBrains IDEs. Editors with little or no
extension API, such as Zed and Helix, get tiers 1 and 2 only.

=== Further refactorings

`c-xrefactory` crossed the "Refactoring Rubicon" early, but only a fraction of the
refactorings that apply to C are automated today. Extending the catalogue — both deeper
versions of what exists (move-function follow-ups, delete-function) and new operations —
is a standing source of value. Several candidates are specified in
<<11-planned-features.adoc#,Planned Features>>.
